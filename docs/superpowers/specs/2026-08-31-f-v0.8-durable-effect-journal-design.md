# F v0.8 Durable Effect Journal — Design

## Scope

F v0.8 closes the remaining local durability gap between an external executor acknowledgement and the canonical patch transaction state. It does not claim distributed exactly-once execution, does not execute external effects, and does not extend F beyond `mutation_scope_only`, `recovery_scope_only`, and terminal `candidate_only` authority.

## Problem

F v0.7 can reconcile a crash after the local transaction already reached `APPLIED` or `ROLLED_BACK` but before the corresponding effect receipt was persisted. A narrower earlier crash window remains:

1. F has persisted an application intent.
2. An external executor performs the effect and returns a stable acknowledgement/receipt.
3. The process crashes before F advances the transaction to `APPLIED` and before the application commit is durably finalized.

The analogous rollback window exists between external rollback acknowledgement and local terminal rollback state.

Without a durable local observation of the executor acknowledgement, F cannot distinguish "executor never ran" from "executor ran and the process died before local finalization". Repeating the external call may be safe only if the executor itself honors the deterministic idempotency key; F cannot prove that property internally.

## Design principles

- External executor facts are observations, not F-owned execution authority.
- Every externally acknowledged effect is recorded as a content-addressed, immutable journal entry before local transaction finalization.
- Journal entries bind exact intent, transaction, patch lineage, deterministic operation/idempotency key, executor receipt reference, executor identity/namespace, and an executor-observed effect-state digest.
- A journal acknowledgement may be replayed only with byte-for-byte semantic equivalence. Any rebinding fails closed.
- Transaction finalization consumes an acknowledged journal entry. It never invokes the external effect.
- Recovery after restart can finalize from the durable journal when the transaction is still in the pre-effect phase, because the journal proves that F already observed an external acknowledgement.
- Recovery can also reconcile the v0.7 later crash windows where transaction state has already advanced.
- A caller may not fabricate broad authority through the journal. Journal records use `observation_only` authority.
- F does not independently authenticate the external receipt. Trust in executor identity and receipt authenticity remains an integration boundary. The journal proves what F observed, not what the external system metaphysically did.
- No single local protocol can guarantee distributed exactly-once behavior without an executor-side idempotency/query contract. v0.8 therefore guarantees exactly-once *local finalization per immutable acknowledgement lineage*, not globally exactly-once external execution.

## Architecture

### 1. `EngineeringEffectJournal`

Create `nolane/external_core/software_engineering_effect_journal.py` as a focused protocol rather than inflating `software_engineering_effects.py` further.

It owns two content-addressed observation types:

- `EngineeringApplicationAcknowledgement`
- `EngineeringRollbackAcknowledgement`

Each record has:

- deterministic acknowledgement id;
- effect intent id + digest;
- transaction id;
- patch ref + digest;
- operation/idempotency ref;
- executor namespace;
- executor receipt ref;
- executor-observed state digest;
- decision `ACKNOWLEDGED`;
- authority `observation_only`;
- canonical digest.

The ledger maintains uniqueness indices by intent, transaction, operation ref, and executor receipt ref. Reusing any unique key with different lineage fails closed.

### 2. Application flow

```text
PRECONDITIONS_VERIFIED
  -> prepare_application()                       # existing immutable intent
  -> journal.acknowledge_application(...)        # durable external acknowledgement observation
  -> finalize_application(ack_id)                # local-only state transition + canonical commit
  -> APPLIED
```

`finalize_application()` validates the acknowledgement against the application intent and immutable mutation-authority lineage. If the transaction is still `PRECONDITIONS_VERIFIED`, it advances to `APPLIED` without calling the executor. If already `APPLIED`, it performs v0.7 reconciliation. Any other phase fails closed.

For compatibility, `commit_application(intent_id, executor_receipt_ref=...)` remains available as a one-call adapter. It creates an acknowledgement using an explicit compatibility executor namespace and state digest derived from the supplied receipt ref, then finalizes it. New integrations should call acknowledgement + finalization separately so the acknowledgement can be durably persisted before transaction advancement.

### 3. Rollback flow

```text
APPLIED/... recoverable
  -> prepare_rollback()                          # existing rollback intent
  -> independent verify_rollback()               # existing restored-state proof
  -> journal.acknowledge_rollback(...)           # durable executor acknowledgement observation
  -> finalize_rollback(ack_id, verification_id)  # local-only terminal state + completion
  -> ROLLED_BACK
```

The rollback acknowledgement additionally binds the rollback intent digest, target-state digest and rollback operation ref. Finalization requires the existing independent verification receipt to match the same target state and intent.

### 4. Snapshot and restore

The unified `SoftwareEngineeringControlPlane` gains an `effect_journal` state member. This is a serialized control-plane schema change, therefore:

- `external.software_engineering.control` compatibility API increments from `0.6.0` to `0.7.0`;
- new journal protocol starts at `0.1.0`;
- existing `external.software_engineering.effects` remains `0.1.0` because its own serialized shape is not changed.

Restore verifies every journal entry against restored canonical intents/transactions and reconstructs uniqueness indices from canonical rows rather than trusting cached index state.

### 5. Coverage invariants

The control plane rejects impossible canonical snapshots:

- a committed application effect with no matching application acknowledgement;
- an application acknowledgement whose intent/transaction/patch/application ref differs from canonical lineage;
- rollback completion with no matching rollback acknowledgement;
- rollback acknowledgement inconsistent with rollback intent or target state;
- duplicate operation/executor receipt keys rebound to different transactions;
- acknowledgement authority broader than `observation_only`.

Backward restore of v0.6 snapshots is intentionally not silently accepted under the v0.7 component identifier. Schema migration must be explicit rather than guessing missing acknowledgement history.

## Error handling

- Unknown intent/verification/transaction: fail closed.
- Rebound executor receipt, operation ref, intent or transaction: `ValueError`.
- Invalid mutation/rollback authority lineage: `PermissionError`.
- Attempt to finalize from a non-recoverable phase: `ValueError`.
- Successful rollback remains impossible without independent `verification-testing` proof.

## Testing strategy

TDD begins with RED cases that the v0.7 API cannot satisfy:

1. application acknowledgement survives snapshot/restore while transaction remains `PRECONDITIONS_VERIFIED`, then finalizes to `APPLIED` without a second external-call API;
2. application acknowledgement cannot be rebound by executor receipt or operation ref;
3. rollback acknowledgement survives snapshot/restore before terminal local transition, then finalizes with independent verification;
4. rollback acknowledgement mismatch fails closed;
5. unified snapshot restore rejects committed/completed effect histories with missing acknowledgement lineage;
6. compatibility `commit_application` and `complete_rollback` continue to produce valid acknowledgement-backed history;
7. authority strings remain `observation_only`, `mutation_scope_only`, `recovery_scope_only`, `candidate_only` at their respective boundaries.

Acceptance remains:

- `Coding AGI Coding Organization Part V` on Python 3.11 and 3.13;
- `Nolane-AI Refoundation Epoch 0` on Python 3.11 and 3.13;
- exact merge-ref/tree identity before merge.
